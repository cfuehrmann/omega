Why nextest didn't move the needle
nextest shaves ~5.6 s off _rust-checks — real, but only ~7% of an ~80 s gate. The e2e step it cannot touch is 81%. That is why just gate feels identical before and after. The win is genuine; the bottleneck is simply elsewhere.

E2E test speedups

1. Merge the two release builds DONE

The e2e recipe builds the mock server and the real server in two separate cargo build --release invocations. On a warm run each still takes ~6.2 s and both recompile omega-agent and omega-server:

# observed in the gate log
Compiling omega-agent … omega-server … omega-mock-server
   Finished `release` … in 6.24s          # cargo build -p omega-mock-server
Compiling omega-agent … omega-server
   Finished `release` … in 6.23s          # cargo build -p omega-server  ← rebuild!

This is feature-unification thrash: building different package subsets in separate invocations resolves the Cargo feature graph differently, so the shared crates are rebuilt with a different feature set the second time. Collapsing both into a single invocation unifies features once and builds each crate once:

# before
cargo build --release -p omega-mock-server
cargo build --release -p omega-server
# after
cargo build --release -p omega-mock-server -p omega-server
Done
Shipped — _rust-e2e-run now builds both binaries in one cargo build --release -p omega-mock-server -p omega-server. Features unify once; the duplicate rebuild is gone. No test-behaviour change.

Much of this is wall-clock waiting (page navigation, element waits) rather than CPU — which is exactly the kind of work that parallelizes well: idle wait on one test overlaps with another. Running even 3–4 at a time could cut the phase to ~15–20 s, the single biggest win available in the whole gate.

Audit result — hermetic except one shared resource
Every test already isolated its ports (127.0.0.1:0 ×2), sessions root (TempDir), and mock-server subprocess. The single blocker was the Chromium profile — exactly the bullet flagged above. chromiumoxide 0.9 points every browser at the shared $TMPDIR/chromiumoxide-runner profile, so a second concurrent Browser::launch aborts on the profile SingletonLock ("Failed to create a ProcessSingleton … profile corruption"). Fix: a unique TempDir per harness via BrowserConfig::builder().user_data_dir(…), held alive for the test and dropped after the browser.
Done — 3.1× on the e2e phase
_rust-e2e-run now runs via cargo nextest run --test-threads 8 (the knee of the curve; -j12/16 buy <1 s more). Measured on the 16-core host: serial 50.9 s → 16.3 s; full gate ~76 s → ~38 s. Stable across 8+ parallel runs (0 flakes); the pick_free_port TOCTOU race never manifested. Reversible: OMEGA_E2E_TEST_THREADS overrides the degree, and without nextest the recipe falls back to serial cargo test.

Mutation-test improvements

Two questions were on the table: how many mutants to run in parallel (-j), and how to stop a pathological mutant from taking down the machine. Both were settled by measurement on this 16-core / 30 GB box. The headline result reverses an earlier, unmeasured assumption: more parallelism does not help — -j1 is optimal across the entire crate-weight spectrum.

Done: revert to -j1 + memory-cap safety SHIPPED

An earlier change (commit 3f93e65) bumped copy-mode sweeps -j2 → -j4 and lifted mutants-edit-tools from -j1 → -j4, on the theory that RAM (≈7 GB/worker) was the only binding constraint. Direct measurement shows that theory was wrong: the bump was a 1.6× pessimization.

Sweep-j1-j2-j4-j8
omega-agent conv_state.rs (30 mutants, heavy)53 s69 s87 s126 s
omega-types tools.rs (18 mutants, lightest crate)13 s12 s14 s23 s

The curve is flat-to-worse for these sweeps and -j8 is up to 2.4× slower. Correctness (caught / unviable, zero missed) was identical at every level.

Corrected mechanism (a first guess retracted). The original explanation — “each mutant already saturates all 16 cores” — is wrong. Direct measurement shows these sweeps run at only ≈16% CPU (2.5 of 16 cores). They are build-dominated: the per-mutant cost is the incremental rebuild and (largely single-threaded) link of the test binary, followed by fast CPU-bound tests. Copy mode gives each worker its own target/, so cross-mutant concurrency does not overlap idle time — it duplicates the build per worker and oversubscribes the one genuinely CPU-heavy phase (codegen). That is why -j1 wins here. It is a regime, not a universal law.

The opposite regime — latency-bound sweeps. When the per-mutant test phase waits on I/O (subprocesses, sockets, monitors, timeouts — and, in the extreme, a browser) cores sit idle and a second concurrent mutant can fill them. The omega-tools suite is exactly this: its tests run at ≈12% CPU (2 of 16 cores), wall-time dominated by waiting. Sweeping format.rs (9 mutants) through it, with the giant-copy confound removed (see the infra note below):

Sweep (latency-bound)-j1-j2-j4-j8
omega-tools format.rs — wall65 s52 s61 s99 s
cores busy (of 16)2.14.48.812.1

Here -j2 is ≈20% faster than -j1 (reproduced across two runs) — the idle cores get filled, and cores-busy climbs with -j. But the optimum is shallow: -j4 already regresses and -j8 is far worse, because the per-mutant build is CPU-bound and copy mode duplicates it, so build contention overtakes the test-overlap win. Real browser e2e is more latency-bound still, but is excluded from mutation testing today (its tests are #[ignore = "browser"] and crates/omega-e2e/** is excluded in .cargo/mutants.toml), so the omega-tools suite is the closest measured analog.

  • All sweeps reverted to -j1 (the measured optimum), undoing the 3f93e65 bump.
  • Every invocation wrapped in {{mutants-mem-cap}} — a systemd-run --user --scope -p MemoryMax=20G -p MemorySwapMax=0 cgroup. See the OOM section below.
  • Scratch hygiene via mutants-prep (unchanged, still valid): every copy-mode recipe runs rm -rf … && mkdir -p … on the scratch dir before the sweep, bounding disk to one sweep's footprint without a failure-path gap.
  • gitignore = true in .cargo/mutants.toml: stop copying gitignored paths into each worker. Without it, copy mode duplicated the 4 GB nested frontends/leptos/target (plus .omega/, mutants.out/) into every worker — exhausting the 16 GB tmpfs TMPDIR at -j4 (No space left on device) and inflating copy cost at every -j. The excluded paths are all build output or logs, never build inputs. This is what makes copy-mode -j scaling viable at all.
Principle codified — the optimum is regime-dependent
-j for mutation testing is not scaled to core count or RAM headroom. The right -j depends on what dominates the per-mutant cost: build-dominated / CPU-bound sweeps (most unit-test crates) → -j1, because copy mode duplicates the CPU-heavy build per worker; latency-bound sweeps whose tests wait on I/O (e.g. omega-tools, and any browser/e2e regime) → a modest -j2 fills the idle cores for ≈20%, but the optimum is shallow and regresses by -j4. Both earlier guesses — “RAM is the binding constraint” and “a mutant saturates all cores” — were wrong; the bench refutes both.

OOM safety: containing runaway mutants SHIPPED

On 2026-06-19 an Omega session was killed mid-sweep by the kernel OOM killer. A cargo-mutants mutant of output_cleaner.rs — i += 1 → i *= 1 in a hand-written byte-index loop — pinned the loop index at zero, so it pushed bytes into an in-memory Vec forever. The process_tools integration test feeds 100–250 KB through that function, so the runaway fired instantly, ballooned to ~22 GB RSS, and triggered a global OOM that took down the whole terminal scope (Omega included). cargo-mutants' wall-clock timeout never fired — memory exhaustion won the race.

Fix: every sweep now runs inside a memory-capped systemd user scope (MemoryMax=20G, MemorySwapMax=0, OOMPolicy=continue). The cap is well above any legitimate -j1 build, far below the ~30 GB global-OOM threshold, and — being cgroup-bounded — means the global system can never OOM no matter how wild the mutant. No swap so the runaway dies in seconds instead of thrashing. The OOMPolicy=continue flag is what makes the sweep not just survive but complete — see below. Validated against the exact crash scenario: the session now survives and the runaway mutants are recorded as caught (memory steady at 27 GB) where it previously died.

Pathological-file sweeps complete cleanly SHIPPED

The first cut of the memory cap was only a session-survival net: the output_cleaner.rs sweep survived but aborted with interrupted instead of recording the runaway mutant. The assumed cause was a group kill — but the kernel log proved otherwise. memory.oom.group is already 0 on a transient user scope, so the kernel kills only the runaway child. The real culprit was systemd's scope-failure policy: when any process in a scope is OOM-killed, systemd marks the scope Failed and SIGTERMs the survivors — taking cargo-mutants down with it.

The one-flag fix is -p OOMPolicy=continue: systemd then just logs the OOM kill and leaves the scope running. cargo-mutants keeps going, sees its test process killed by signal, and records the mutant as caught — naming it in the normal output, exactly what an operator (or the agent) needs to see. Both constraints are met: no perf cost (the cap only ever fires on a genuine runaway, which the OOM kills in seconds) and full visibility (the culprit mutant is named with its outcome).

Validated end-to-end: the two output_cleaner.rs runaway mutants (+= → *= at :72 and :75) now report 2 mutants tested in 36s: 2 caught, cargo-mutants exits 0, and the session's memory never moves off 27 GB.

Alternatives considered and rejected: a per-test ulimit -v wrapper (more moving parts, and virtual-memory limits misfire on threaded Rust binaries); a tight --timeout (the allocating loop hits the cap in seconds, so the timeout would have to be aggressive enough to false-fire on slow legitimate mutants); and --exclude-re / #[mutants::skip] on the loop mutants (hides a real coverage question instead of answering it). OOMPolicy=continue dominates all three: zero overhead, no false positives, and the runaway is still exercised and reported.

Convert copy-mode sweeps to --in-place everywhere TODO

With -j1 now the optimum, copy mode's only advantage (running several mutants at once) is moot — yet several recipes still copy the whole project per run. --in-place mutates the real source file and reverts it, skipping the copy entirely: on the conv-state bench that was ~53 s vs ~65 s for copy -j1 (≈15–20% faster). The heavy crates (omega-agent, omega-core, omega-server) already use --in-place for this reason.

Why it's deferred, not done
In-place leaves the working tree dirty if a run is interrupted (Ctrl-C, crash, or the very OOM that just bit us) — recoverable with git checkout, but a real hazard on a machine that just crashed mid-sweep. Copy mode is the safer default; the speed-up is real but secondary, so this is a deliberate trade rather than an oversight.

Appendix: why the 358H is no faster than the 1165G7

Expectation: a 16-core Core Ultra X7 358H should beat the old 4-core/8-thread i7-1165G7. Observed: gate ~80 s vs ~72 s — slightly slower. This is not a paradox.

i7-1165G7 (old)Core Ultra X7 358H (new)
Topology4 P-cores / 8 threads, homogeneous4 P + 8 E + 4 LP-E, no HT (16×1)
Per-core clockall P, up to 4.7 GHzP 4.7–4.8 / E 3.7 / LP-E 3.3 GHz
Best single-thread~4.7 GHz~4.8 GHz (≈ parity)

Three reasons the extra silicon doesn't help here:

  1. The bottleneck is serial. 81% of the gate is the e2e step, which runs --test-threads=1 plus serial release builds. By Amdahl's law, a serial phase sees zero benefit from more cores — 12 of the 16 sit idle through the dominant ~52 s. Core count is simply the wrong axis for this workload.
  2. Per-thread, the 358H is not faster — and can be slower. Its best P-core (4.8 GHz) only matches the 1165G7's P-core (4.7 GHz). But on a hybrid chip the scheduler may place a lone, latency-insensitive-looking thread on an E-core (3.7 GHz) or LP-E core (3.3 GHz) — 20–30% slower per thread than the old all-P-core chip.
  3. It is thermal-throttling. See below — the strongest single contributor, and the most actionable.
Takeaway
The fix for gate wall-time is not the CPU — it is removing the serial bottleneck (e2e parallelization, §2 above) and keeping the chip off its thermal wall (below). Once e2e runs N-wide, the 358H's extra E-cores finally have work to do and the core-count advantage materializes.

Thermal throttling & thermald

Measured on this host after only ~3 h uptime, in the merely balanced power profile:

The chip is cooling-limited, not policy-limited — it throttles hard even in balanced. Reactive Tjmax throttling is the worst case: clocks are allowed to climb until 100 °C, then slammed to the floor, then recover — an oscillation that wastes performance. The cooler-running 4-core 1165G7 sustains its clocks better, which is a large part of why it finishes the (serial) gate sooner.

Recommendation — install thermald (the temperature-based throttle you want) DONE

Installed & active as of this session: thermald 2.5.12, enabled, running --systemd --dbus-enable --adaptive (adaptive mode uses the INT3400 DPTF tables). Enabled via:

sudo pacman -S thermald
sudo systemctl enable --now thermald

thermald reads the DTS / INT3400 DPTF sensors and throttles proactively via RAPL and P-state caps before Tjmax, holding a cooler, steadier clock. On a cooling-limited part this typically raises sustained throughput while lowering peak temperature — safety and speed in the same move. It coexists with power-profiles-daemon (PPD owns governor/EPP/platform-profile; thermald owns the thermal limit). Optionally cap the target with a custom /etc/thermald/thermal-conf.xml if you want a ceiling below 100 °C.

Do NOT just force the performance governor
Pinning the governor/EPP to performance without a thermal daemon would only feed the fire — it is already throttling in balanced. Add the temperature throttle first; then a higher power profile is safe because thermald caps the heat.
How to verify the win

Watch the counter live across a gate run: watch -n1 cat /sys/devices/system/cpu/cpu0/thermal_throttle/package_throttle_count. Run just gate before and after enabling thermald and compare the delta in that count, the peak sensors package temperature, and the gate wall-time. Expect fewer throttle events, a lower peak temp, and equal-or-better wall-time.
