Why nextest didn't move the needle
nextest shaves ~5.6 s off _rust-checks — real, but only ~7% of an ~80 s gate. The e2e step it cannot touch is 81%. That is why just gate feels identical before and after. The win is genuine; the bottleneck is simply elsewhere.

E2E test speedups

1. Merge the two release builds DONE

The e2e recipe builds the mock server and the real server in two separate cargo build --release invocations. On a warm run each still takes ~6.2 s and both recompile omega-agent and omega-server:

# observed in the gate log
Compiling omega-agent … omega-server … omega-mock-server
   Finished `release` … in 6.24s          # cargo build -p omega-mock-server
Compiling omega-agent … omega-server
   Finished `release` … in 6.23s          # cargo build -p omega-server  ← rebuild!

This is feature-unification thrash: building different package subsets in separate invocations resolves the Cargo feature graph differently, so the shared crates are rebuilt with a different feature set the second time. Collapsing both into a single invocation unifies features once and builds each crate once:

# before
cargo build --release -p omega-mock-server
cargo build --release -p omega-server
# after
cargo build --release -p omega-mock-server -p omega-server
Done
Shipped — _rust-e2e-run now builds both binaries in one cargo build --release -p omega-mock-server -p omega-server. Features unify once; the duplicate rebuild is gone. No test-behaviour change.

2. Parallelize the browser tests DONE

Much of this is wall-clock waiting (page navigation, element waits) rather than CPU — which is exactly the kind of work that parallelizes well: idle wait on one test overlaps with another. Running even 3–4 at a time could cut the phase to ~15–20 s, the single biggest win available in the whole gate.

Audit result — hermetic except one shared resource
Every test already isolated its ports (127.0.0.1:0 ×2), sessions root (TempDir), and mock-server subprocess. The single blocker was the Chromium profile — exactly the bullet flagged above. chromiumoxide 0.9 points every browser at the shared $TMPDIR/chromiumoxide-runner profile, so a second concurrent Browser::launch aborts on the profile SingletonLock ("Failed to create a ProcessSingleton … profile corruption"). Fix: a unique TempDir per harness via BrowserConfig::builder().user_data_dir(…), held alive for the test and dropped after the browser.
Done — 3.1× on the e2e phase
_rust-e2e-run now runs via cargo nextest run --test-threads 8 (the knee of the curve; -j12/16 buy <1 s more). Measured on the 16-core host: serial 50.9 s → 16.3 s; full gate ~76 s → ~38 s. Stable across 8+ parallel runs (0 flakes); the pick_free_port TOCTOU race never manifested. Reversible: OMEGA_E2E_TEST_THREADS overrides the degree, and without nextest the recipe falls back to serial cargo test.

Mutation-test improvements

Two distinct levers: how many mutants run in parallel, and how much disk the scratch trees consume. The old machine conflated them — it throttled parallelism to keep disk bounded. With 1.8 TB free, they are now decoupled.

Done: -j4 parallelism & disk hygiene SHIPPED

  • Copy-mode sweeps bumped -j2 → -j4, and the disk-pinned mutants-edit-tools lifted from -j1 → -j4. The binding constraint is now RAM (30 GB ≈ 7 GB/worker), not disk or cores — a GNU jobserver already caps total build tasks at NCPUS across workers, and cargo-mutants' own guidance warns against scaling -j to core count.
  • Scratch hygiene via mutants-prep: every copy-mode recipe now runs rm -rf … && mkdir -p … on the scratch dir before the sweep. This bounds disk to a single sweep's footprint and cleans up leftovers from interrupted/failed runs — without a failure-path gap (a trailing cleanup line would be skipped when a survivor makes the recipe exit non-zero).
Principle codified
Parallelism is driven by RAM, never throttled to keep a disk number down. Disk is bounded by cleanup, not by lowering -j. The two are independent knobs.

Pending: convert wide in-place sweeps to copy-mode TODO

~17 sweeps still use --in-place, which is inherently sequential (one shared source tree, cannot parallelize). They were chosen only to dodge the ~6 GB target-tree copy — a disk worry that is now both abundant and self-cleaning. The wide ones (many mutants) should become copy-mode -j4 to gain parallelism; the narrow --re-scoped agent.rs sweeps (often a handful or zero mutants) should stay in-place — copying a 6 GB tree ×4 for 0–3 mutants is pure waste.

Appendix: why the 358H is no faster than the 1165G7

Expectation: a 16-core Core Ultra X7 358H should beat the old 4-core/8-thread i7-1165G7. Observed: gate ~80 s vs ~72 s — slightly slower. This is not a paradox.

i7-1165G7 (old)Core Ultra X7 358H (new)
Topology4 P-cores / 8 threads, homogeneous4 P + 8 E + 4 LP-E, no HT (16×1)
Per-core clockall P, up to 4.7 GHzP 4.7–4.8 / E 3.7 / LP-E 3.3 GHz
Best single-thread~4.7 GHz~4.8 GHz (≈ parity)

Three reasons the extra silicon doesn't help here:

  1. The bottleneck is serial. 81% of the gate is the e2e step, which runs --test-threads=1 plus serial release builds. By Amdahl's law, a serial phase sees zero benefit from more cores — 12 of the 16 sit idle through the dominant ~52 s. Core count is simply the wrong axis for this workload.
  2. Per-thread, the 358H is not faster — and can be slower. Its best P-core (4.8 GHz) only matches the 1165G7's P-core (4.7 GHz). But on a hybrid chip the scheduler may place a lone, latency-insensitive-looking thread on an E-core (3.7 GHz) or LP-E core (3.3 GHz) — 20–30% slower per thread than the old all-P-core chip.
  3. It is thermal-throttling. See below — the strongest single contributor, and the most actionable.
Takeaway
The fix for gate wall-time is not the CPU — it is removing the serial bottleneck (e2e parallelization, §2 above) and keeping the chip off its thermal wall (below). Once e2e runs N-wide, the 358H's extra E-cores finally have work to do and the core-count advantage materializes.

Thermal throttling & thermald

Measured on this host after only ~3 h uptime, in the merely balanced power profile:

SignalValueMeaning

RAPL PL1 / PL2 / peak35 / 80 / 175 W80 W burst in a thin chassis → 100 °C fast
thermal daemon (at time of diagnosis)nonethermald not installed; only power-profiles-daemon

The chip is cooling-limited, not policy-limited — it throttles hard even in balanced. Reactive Tjmax throttling is the worst case: clocks are allowed to climb until 100 °C, then slammed to the floor, then recover — an oscillation that wastes performance. The cooler-running 4-core 1165G7 sustains its clocks better, which is a large part of why it finishes the (serial) gate sooner.

Recommendation — install thermald (the temperature-based throttle you want) DONE

Installed & active as of this session: thermald 2.5.12, enabled, running --systemd --dbus-enable --adaptive (adaptive mode uses the INT3400 DPTF tables). Enabled via:

sudo pacman -S thermald
sudo systemctl enable --now thermald

thermald reads the DTS / INT3400 DPTF sensors and throttles proactively via RAPL and P-state caps before Tjmax, holding a cooler, steadier clock. On a cooling-limited part this typically raises sustained throughput while lowering peak temperature — safety and speed in the same move. It coexists with power-profiles-daemon (PPD owns governor/EPP/platform-profile; thermald owns the thermal limit). Optionally cap the target with a custom /etc/thermald/thermal-conf.xml if you want a ceiling below 100 °C.

Do NOT just force the performance governor
Pinning the governor/EPP to performance without a thermal daemon would only feed the fire — it is already throttling in balanced. Add the temperature throttle first; then a higher power profile is safe because thermald caps the heat.
How to verify the win

Watch the counter live across a gate run: watch -n1 cat /sys/devices/system/cpu/cpu0/thermal_throttle/package_throttle_count. Run just gate before and after enabling thermald and compare the delta in that count, the peak sensors package temperature, and the gate wall-time. Expect fewer throttle events, a lower peak temp, and equal-or-better wall-time.
