File-Editing Tool — Error Analysis & Redesign

Status: Implemented — single edit_file + new multi_edit_file, optional replace_all. The fuzzy cascade was subsequently removed in favour of exact matching with informative errors: a deeper root-cause study of the old_text_not_found failures (see addendum) showed the cascade would mostly "rescue" genuine content mistakes (wrong numbers, dropped words, glyph-vs-escape) by editing the wrong place, and whitespace is often load-bearing. Input-shape leniency also deliberately omitted. The schema descriptions below document the pre-change baseline and the rationale. · Scope: reduce the LLM error rate when editing files in Omega · Source data: all events.jsonl logs under .omega/sessions/ (335 sessions) · Comparison agents: Claude Code, opencode, forgecode, pi-mono.

In one sentence

Omega's single edit_file tool fails on 6.8 % of calls; three-quarters of those failures are inexact old_text matches and one-sixth are malformed calls induced by the mandatory array-of-objects schema. We will split it into a flat single-edit tool plus a separate multi-edit tool, add an optional replace_all, and add an opencode-style fuzzy-match cascade — while deliberately not coercing malformed input, so tool/argument mismatches stay visible.

1 · Method

Every session under .omega/sessions/ writes an append-only events.jsonl. For each session I correlated every edit_file tool-call with its matching tool-result (by id), classified the failures by result message, and — for the malformed calls — inspected the actual argument shape the model emitted (key set, JSON type of replacements). I also measured recovery: whether a failed call was followed by a successful edit_file later in the same session.

4 · The malformed-call cases, decomposed

The 36 structural errors split into exactly two shapes. Notably, none were a literal empty array [] — the model never "forgot" to fill the array; it produced the wrong container for it.

Malformed shapeCountWhat the model emitted
replacements as a JSON string 29 "replacements": "[{\"new_text\": …}]" — the whole array serialized into a string instead of a real JSON array.
flattened single edit 7 top-level {path, old_text, new_text} with no replacements key — i.e. the Claude-Code single-edit shape.
truly empty array [] 0 —
Cross-model, not Omega-specific

pi-mono's edit tool contains this exact guard, with a revealing comment: 

// Some models (Opus 4.6, GLM-5.1) send edits as a JSON string instead of an array
if (typeof args.edits === "string") { … JSON.parse … }

So the "stringified array" tendency is a known behaviour of frontier models when faced with an array-of-objects parameter — strong evidence that the schema shape is what induces the error, not Omega's wiring.

6 · How other agents do it

Every comparison agent is more lenient than Omega today, and two of them defend against precisely the malformed shapes above. The split between a flat single-edit tool and a separate multi-edit tool is the Claude-Code pattern.

AgentSchemaMatching / leniency
Omega (today) edit_file{path, replacements:[{old_text,new_text}]} — required array-of-objects strict: exact byte match only; no fuzzy fallback, no coercion
Claude Code flat Edit{file_path, old_string, new_string, replace_all?} + separate MultiEdit{file_path, edits:[…]} exact match; replace_all for renames
opencode flat {filePath, oldString, newString, replaceAll?} — no array 9-strategy fuzzy cascade: simple → line-trimmed → block-anchor → whitespace-normalized → indentation-flexible → escape-normalized → trimmed-boundary → context-aware → multi-occurrence
forgecode flat FSPatch{file_path, old_string, new_string, replace_all} + separate FSMultiPatch{edits:[…]} #[serde(alias)] accepts path/search/content key variants; fuzzy-search repository
pi-mono array-based {path, edits:[{oldText,newText}]} prepareArguments() coerces both Omega failure modes (stringified array → parse; flattened → wrap)

7 · Decided design

Decisions (locked in)
  • Two tools planned — a flat single-edit tool and a separate multi-edit tool, in the Claude-Code style. The flat single-edit shape is the common case and avoids the array-of-objects parameter that induces the stringified-array error.
  • Optional replace_all planned — addresses the old_text_ambiguous class (renames / repeated snippets); matches Claude Code, opencode, forgecode.
  • opencode-style fuzzy-match cascade planned — the biggest lever, targeting the 75.6 % old_text_not_found class. Try exact match first, then progressively more tolerant strategies, keeping a "must resolve to exactly one location" guard for safety.
  • Lenient input-shape coercion deliberately not now — we will not auto-fix stringified arrays or flattened edits. A mismatch between tool type and arguments may be a thinking error worth observing; coercing it would hide the signal. Keep monitoring before deciding.
  • System prompt updated to match planned — the current rule "never call edit_file on the same file twice in a row" exists only because the array is mandatory; with a flat single-edit tool it should be revised, and the two-tool choice (single vs multi) should be described.
Why keep strict input-shape handling?

Coercion (pi-mono / forgecode style) would erase ~17 % of failures cheaply, but it also erases the evidence. If a model sends a stringified array or a flattened edit, that is the model picking the wrong contract — potentially a reasoning slip we want to see and measure, especially right after introducing two distinct tools. We keep it loud for now and revisit once the new tools have produced data.

8 · Implementation plan not started

Suggested order (open to revision):

  1. Single-edit tool + replace_all. Smallest, self-contained unit; establishes the flat schema and exact-match-then-replace_all semantics. Tested through execute_tool.
  2. Fuzzy-match cascade. The highest-impact change; layer it under the single-edit tool's matcher so the multi-edit tool inherits it. Port opencode's strategies, each with the single-location guard.
  3. Multi-edit tool. Built on the same matcher; applies a sequence of edits to one file, failing the whole call if any edit doesn't resolve.
  4. System prompt. Describe single vs multi, document replace_all, drop/replace the "twice in a row" rule.
  5. Retire edit_file (or keep transitionally) once the two replacements are in place.

Rationale for this order: each step is independently shippable and testable, and the fuzzy cascade — the dominant win — sits at the bottom of the stack so both tools benefit from it. Per project conventions, each non-trivial unit gets red/green tests through the public tool API plus a targeted cargo mutants run.

Touchpoints — everywhere a tool is registered

Adding/removing a tool is a cross-crate change. The Rust types lead; schema, prompt, and UI follow (Contract Authority rule). Missing any one of these silently drops the new tool from a surface — the tool-choice dialog in particular has an explicit invariant that will hide an unlisted tool.

Addendum — root-cause study of old_text_not_found, and why the cascade was removed

The original recommendation (port opencode's fuzzy cascade) was made before we knew why the not_found failures (75.6 % of all errors) actually occurred. A follow-up study tried to recover, for each failure, the file contents the model was matching against. Reconstructing file state from a prior read proved unreliable (often the file was located via search and never fully read, or our copy was stale after the model's own earlier edits). The trustworthy signal was the model's own successful retry of the same edit: the retry text is verified-present, so the difference from the failed attempt is the root cause. At high similarity this yielded 37 clean, character-diff-verified cases.

Root cause of the failed matchShareImplication
Genuine wrong content (missing :, wrong region, glyph vs source escape e.g. ' vs \u{2019})~73 %model had the wrong bytes → should error
Interior misquote (first/last line match, middle wrong: 5→2, dropped words)~13 %a block-anchor/fuzzy matcher would edit the wrong content
Pure indentation drift~8 %the only genuinely cosmetic, rescuable class
External change between attempts~5 %stale → should error

Two conclusions reshaped the design. First, cosmetic whitespace is a small minority, not the dominant cause — so an elaborate forgiving matcher is unjustified. Second, the 13 % interior-misquote cases are direct evidence that aggressive matching does harm: it would silently replace a block whose interior the model got wrong. Combined with the fact that whitespace is frequently load-bearing (Python, YAML, Makefiles, aligned columns, string literals), the chosen policy is exact matching, forgive nothing — and move all the cleverness into read-only diagnostics that explain a failure (whitespace/indentation drift, CRLF line endings, multiple matches with line numbers) without ever acting on a guess. The nine-strategy cascade (and its Levenshtein/​similarity machinery) was deleted; the matcher shrank from ~900 to ~270 lines.
