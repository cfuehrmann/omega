Async Monitors — Invariants, Decisions & Future Work

CORE SHIPPED This doc keeps only what's needed to move forward: architectural invariants (must-holds), locked-in decisions (must-not-revert), the future menu, and a resume map. The history of how each piece was built lives in the code and its tests.

What exists

An agent can monitor(description, command) to run a background shell command whose stdout lines are injected as role:user at the next seam (no preemption), watch/steer it from the Web UI, and stop_monitor(id). run_background(command) is a silent monitor — it returns immediately with { id, logFile, pid }, redirects output to logFile (zero deliveries), and fires one MonitorStopped on exit; write_stdin/stop_monitor work on jobs and monitors alike, keyed by id. Input (human + monitor) flows through one queue; loop controls are Queue / Halt / Abort, and the UI can delete an individual pending queued prompt before it is delivered. A first-class event sink lets out-of-band events (stderr, control actions) reach events.jsonl + UI when they happen.

1. Invariants & locked-in decisions

Seam & loop correctness (forced by the Anthropic Messages API)

  • Two roles only. Anything not generated by the model (tool results, monitor output, human input) enters as role:user. The synthetic flag is a harness/UI marker only.
  • tool_use → tool_result is rigid — the result is the very next message; nothing inserts between them.
  • Two legal injection seams. Seam A: after end_turn (idle). Seam B: after the tool_result blocks answering a tool_use. The loop drains the input queue only at these two points — so “never inject mid-pair” is structural, not a decision that can be gotten wrong.
  • No context-level preemption. Monitors never interrupt an in-flight message. The only pre-boundary action is Abort (transport-level), kept as a separate explicit interrupt.
  • ⛔ Monitors are out-of-band, never a blocking tool. A long/blocking tool holds Seam B shut → starvation (the former wait_for_output problem this feature exists to prevent — wait_for_output was deleted).
  • Single writer for context-bound events — the loop appends; monitors enqueue. (Generalised by the event sink for non-context events — see below.)
  • Park/terminate is defined. Park iff a live monitor or queued item exists, else terminate; never hang when nothing can fire. Parked, the loop selects over {queue item, roster-changed}; roster-changed fires when the live set shrinks without a drainable item (e.g. the last live monitor going away without enqueuing a drainable item while parked).
  • Process-tree reaping on stop() and session end (process-group kill); no orphans.

Contract Authority & schema

  • The Rust OmegaEvent is the canonical schema (crates/omega-types/src/events.rs). Persistence, WS, and UI are derived projections. A semantic change requires a syntactic one (new variant), never a silent alias; update the UI to the types, never the reverse. Old logs failing to deserialize a renamed variant is intended signal, not a bug to paper over.
  • ⛔ Derived projections must be derived, not hand-mirrored. Frontend event frames deserialize straight into OmegaEvent; a drift-guard test round-trips every variant; an unparseable frame surfaces visibly. (Re-introducing a parallel hand-kept WsMessage enum is exactly the drift that made monitor deliveries silently invisible.) Genuinely transport-only envelope frames are the only hand-written part; a new one must not collide tags with an event.
  • Persistence shape. events.jsonl = all events; context.jsonl = derived per-record projection (keyed by ContextHash) that excludes MonitorStderr. Merging consecutive user-role records into one API message is request-assembly (project_messages()), leaving the per-record log un-merged so ContextHash foreign keys stay stable.
  • Projection rules. The fold skips MonitorStderr; MonitorDelivery projects role:user; an unexpected MonitorStopped (StoppedByUser / ProcessExited / ProcessCrashed) projects so the agent learns, while StoppedByAgent and StoppedBySessionEnd do not.
  • Roster is ephemeral — runtime-only, never persisted or reconstructed. WsMessage::MonitorRoster is transport-only (not an OmegaEvent), pushed seam-aligned on connect/reset/resume and after each monitor event.

Unified input model

  • ⛔ One persistent run loop + one InputQueue for human and monitor input, tagged by source. (Do not revert to parking inside send_message: it held the agent lock for the whole turn and deadlocked a fresh UserMessage.)
  • role:user is a projection, not a storage decision. Human messages stay UserMessage, monitor deliveries stay MonitorDelivery; merged late by project_messages(). Human/monitor symmetry falls out for free.
  • Three orthogonal controls: Queue (always enqueue, deliver at next seam), Halt (stop at next seam and wait), Abort (cancel the in-flight block). The retired pause/continue-for-injection machinery is guarded by a source-scan test so it can't grow back.
  • UI kill targets queued prompts only, not live monitors. The UI exposes DeleteQueueItem{enqueued_at} to drop a single pending prompt before it is delivered; there is deliberately no UI kill for a running monitor. Monitors are stopped by the agent (stop_monitor), on natural process exit, or at session end — consistent with the no-auto-stop / visibility-over-control stance. StoppedByUser remains in the schema (and projects when present) but is currently unreachable at runtime; re-add a monitor kill control only on evidence.

Event sink — event-time vs commit-time

  • ⛔ Event-time and commit-time are independent; keep both. Event-time = embedded time / UUIDv7 event_id (when it happened). Commit-time = file/arrival order in events.jsonl (when recorded). Never sort the log by time; the UI shows arrival order with each row's own time. Their divergence is signal (skew/latency/races), not noise.
  • One occurrence = one creation = one time = one event_id, routed to both disk and wire from that single value. Stamp time at the moment of occurrence; append whenever. (Re-deriving a fresh now at broadcast is the double-stamp bug.)
  • Sink contract: emit(event) appends + broadcasts in arrival order, from any caller at any time, with no coordination — EventStore is stateless and its append is O_APPEND/per-line atomic; ws_tx is a multi-producer sender resolved live (replaced on reconnect).
  • User action vs effect. A model/effort change is recorded at action-time (out-of-band, even mid-turn); its effect is turn-aligned — drive_turn snapshots model+effort at entry, so a mid-turn change applies next turn, never to the in-flight one.
  • Phase A (additive sink alongside the loop's path) is shipped; full unification of emission (one emitter, observers as projections — with control kept out of the bus) is future work, tracked at §3 item 1.

Guardrail stance & teaching copy

  • Explorative minimalism. Add only correctness rails; skip the public-serving rails Anthropic adds for a broad audience; iterate by observing the single agent. UI observability is what earns skipping automated kill.
  • Currently dropped (re-add only on evidence): default/max timeout_ms, auto-stop of chatty monitors, line-buffering nagging. Verified prior art (Claude Code) keeps auto-stop + line-buffering — flagged in Future work.
  • No auto-stop — runaway monitors are caught by visibility (logs + UI fired-count), not automation.
  • Teaching copy is load-bearing for usability. Tool descriptions + system-prompt addendum must say: monitor output is not the human; do not fabricate/guess output; after starting, end your turn and wait; stop when no longer needed. The tool result stays neutral bare data (a “stop it when done” sentence tipped Sonnet into killing monitors instantly).
  • Lifecycle decisions. Clean shutdown kills all trees + best-effort MonitorStopped; a hard crash leaves a dangling MonitorStarted (intended forensic signal). Resume forks a new session — no live-monitor inheritance, nothing to reconcile. Headless is benchmark-only, bounded externally + session-end cleanup.

Background jobs are silent monitors (built)

  • ⛔ A background job is a monitor whose command redirects its own output to a log file. run_background does not spawn directly; it calls the same MonitorManager::spawn the monitor tool uses, with the command pre-wrapped exec > {logFile} 2>&1\n{cmd}. There is no new type, delivery-mode flag, or schema change — the silence is a property of the command (the redirect empties the stdout/stderr pipes), not a separate code path. Reverting to a bespoke spawn path would make jobs unobservable again (no roster entry, no event-log trail).
  • ⛔ No schema change: a job reuses MonitorStarted/MonitorStopped with zero MonitorDelivery in between. The logFile is recorded implicitly in the wrapped command string; do not add a logFile/kind/delivery_mode field. A wrapped job emits exactly one MonitorStopped (the completion notification, carrying the exit code); a streaming monitor emits many deliveries + one stop. Both always end with exactly one stop — the only difference is the stream-derived delivery count.
  • ⛔ wait_for_output is deleted; do not reintroduce a blocking wait. “Return now, notified on exit” is the whole point (a blocking wait holds Seam B shut → starvation). “Wait for ready” is a shell idiom inside the command (until grep -q '…' LOG; do sleep; done whose exit is the condition) or a streaming monitor for progressive signals; the old pattern/minBytes/timeoutMs params become shell idioms. The system prompt and tool descriptions teach: returns immediately, read the logFile for output, do not poll.
  • ⛔ One registry, keyed by monitor id. The global processes() table (state.rs) is retired; jobs and monitors share the manager's roster. run_background returns { id, logFile } (pid as an info field); stop_monitor(id) stops a job for free. Do not resurrect a second process table.
  • ⛔ The manager spawns with stdin = piped; write_stdin is keyed by id and serves both jobs and monitors. stdin is a separate pipe — the exec > LOG 2>&1 redirect touches stdout/stderr only, so the wrapped job can still be fed input. The write_stdin handle is the monitor id, not a pid. Consequence (intended): a monitor command that reads stdin now blocks for input instead of getting immediate EOF (matches today's run_background).
  • The log file is “tee always” applied to a live process. Finite tools capture-then-tee into cache/{run,fetch}/; an unbounded job tees live via fd redirection into cache/bg/<ts>-<id>.log. It is the only copy of a silent job's output; read_file is the pull path (mirrors Claude's BashOutput buffer).

2. Design reference: Claude Code’s model & expressing waits

Forward-looking reference for the open follow-ups (per-monitor timeout_ms, auto-stop, evidence-gathering). The decisions that shipped are recorded as ⛔ invariants in §1; this section keeps only the design knowledge those decisions rest on and the questions they leave open.

2.1 What Claude Code does (reverse-engineered)

First, the mechanic stated plainly. There is one tool — Bash — with a run_in_background:true parameter. The LLM emits one tool call whose command is an ordinary shell string; any grep/until/sleep in it is shell inside that one command, not extra tools. The agent (the Omega-equivalent runtime) then does two dumb things: spawn the process and return immediately, and — when that process exits — inject one synthetic notification at the next seam. The runtime's trigger is uniform: process exit. All the “wait for the right moment” intelligence lives in the command string the LLM wrote. The LLM never polls (it is told not to); the runtime watches.

So the decisive question is “does the process exit at the exact moment you care about?” — it tells you directly whether you need one background command or two:

Does it exit when you care?CommandsExample
Yes — a finite job that exits when done One background command; its own exit is the notification the gate, a build, a test suite, cargo mutants
No — long-lived, your moment is mid-stream Two: the long-lived job + a short-lived waiter whose own exit encodes the condition (until grep -q 'Ready'; do sleep 0.5; done). Or one Monitor streaming the line. a dev server printing “Ready in”; one specific log line

The slow-gate case — the common one — is one command: the gate exits on its own, so its exit is the signal; no waiter needed. A second moving part is only for an early signal (e.g. notify on the first FAILED line before the gate finishes), which is the streaming case below.

Claude's own copy sorts the same split by how many notifications you need — not by “foreground vs background”:

NeedMechanismBehaviour
One — “tell me when the build finishes / the gate passes” Bash with run_in_background:true. For a finite job (gate/build) the command is just the job — it exits on its own. For a long-lived job whose moment is mid-stream, the command is a waiter written to exit on the condition (until grep -q "Ready in" dev.log; do sleep 0.5; done). Silent while running; one completion notification on exit. Output pulled on demand via BashOutput. Explicit rule: “you'll be notified when it completes — do not poll.”
One per occurrence, indefinitely — “every time an ERROR line appears” Monitor with an unbounded command (tail -f, inotifywait -m, while true) Each stdout line becomes a notification (interrupt). Runs until timeout or TaskStop; persistent:true for session-length watches.
One per occurrence, until a known end — “emit each CI step, stop when the run completes” Monitor with a command that emits lines and then exits Push per line; the watch ends when the command exits.

Supporting cast: BashOutput(bash_id, regex?) = pull output on demand (optional filter); KillShell / TaskStop = kill/cancel; ScheduleWakeup = a fallback heartbeat timer (1200–1800 s) used only as a backstop when a Monitor is the real wake signal. Monitor specifics worth pinning:

  • Timeout is mandatory-ish. “Timeout → killed.” Unbounded commands stay armed until timeout even after the event fired — hence the explicit steer to use run_in_background+until for single notifications, not tail -f | grep -m1.
  • Auto-stop on volume. “Monitors that produce too many events are automatically stopped; restart with a tighter filter.” (Confirms the auto-stop prior art we dropped.)
  • 200 ms batching of stdout lines into one notification; stdout-only triggers (stderr goes to the output file, readable on demand).
  • Heavy script-quality copy: per-line flushing (grep --line-buffered, awk … fflush(), never | head -N), and “silence is not success” — the filter must match every terminal state (crash/hang/OOM), not just the happy path.

The load-bearing finding

Claude has no synchronous blocking wait at all. The “wait for X” use case — the case a blocking wait_for_output would serve — is served by run_in_background + an until loop that exits when the condition is true, yielding one notification. That is a non-blocking wait_for_output: the agent's turn is free to continue or end while the wait happens out-of-band.

2.2 Expressing bounded/conditional waits without a blocking tool

Background jobs are non-blocking (§1): a job returns immediately and notifies on exit. “Wait for a condition” is therefore expressed in the command, not a tool param. The table maps each tuned param of the deleted blocking wait_for_output onto its shell-idiom equivalent — the reference an agent (or a future timeout_ms design) needs:

wait_for_output paramWhy it was tunedMonitor-world equivalent
pattern (JS regex)return as soon as the ready/failure line appearsgrep -qE 'PATTERN' in the loop guard
minBytesreturn once meaningful output exists, no known markerbyte-count check on the log
timeoutMs (required)never hang foreverno monitor equivalent today — needs a timeout N wrapper or a new per-monitor timeout
pid (early-exit)stop waiting the instant the process diesloop must also break on kill -0 $pid || break
tail-biased 200 KB capmost-recent output is what mattersoutput retrieval via read_file on the log

Every param has a shell-idiom home except timeoutMs (“never hang forever”): today that is a timeout N … wrapper inside the command. A first-class per-monitor timeout_ms — the one bounded-wait affordance worth restoring — is tracked as §3 item 2. A blocking wait_for_output is not the way back: it holds Seam B shut (§1).

2.3 Where to gather evidence

The blocker is evidence: we need a task the agent wants to wait on and has the opportunity to. Omega's own workflow supplies several — these are where to look first:

  • Mutation testing (cargo mutants) — minutes-to-tens-of-minutes; the agent has a real incentive to react to the first survivor rather than block. The strongest candidate.
  • The gate / full cargo test — slow enough that blocking wastes a turn; a monitor watching for the first failure line is the natural shape.
  • Web-UI dev server (trunk serve / Leptos watch) — a classic “wait for Ready in, then keep tailing for errors” case spanning needs 1 and 2.
  • Long release builds — pure need-1 (“tell me when done”).

Instrumentation question alongside: what do we record to tell whether the agent chose well — streaming monitor vs. silent run_background vs. blocking run_command? The fired-count + commit-time/event-time skew already in the log is a start.

3. Future work (sorted by attractivity)

Ranked by (value × readiness) ÷ (cost × risk). Nothing is scheduled — this is the menu. Two items that used to head this list have shipped: the blocking-wait / one-shot-vs-streaming question (now §1 invariants), and the seam-typestate guard that lifts model-facing protocol correctness from an emergent property into a structural one — a register automaton (Empty / Idle / AwaitingAssistant / AwaitingToolResults{pending}) at the single append_record context-append chokepoint, enforcing the strict tool_use↔tool_result id bijection, with a dedicated ConversationInvariantViolated forensic event written before a hard fail on any violation. A uniform event-emission architecture (one emitter; observers as projections) now leads what remains, superseding the former “Phase B”. The evidence-deferred cluster (per-monitor timeout, auto-stop) follows.

  1. Uniform event emission — one emitter, observers as projections. (Supersedes the former “event sink — Phase B”.) Target: the agent emits each event once, to a single emitter; every observer is a projection that subscribes — events.jsonl the comprehensive, durable, ordered projection; the frontend a live, best-effort one; tests subscribe a recorder. This makes missing/double-emit structurally impossible (one emit point) and makes each projection independently testable — notably the events→events.jsonl transform, which today is only exercisable through a full agent run. Today there are two emission paths: the loop's event_store.append() + yield (in-turn events) and the sink's emit() (out-of-band: model/effort change, halt, monitor stderr). The durable record is not the problem — both paths call append(), so events.jsonl is already complete and correct. The split shows up in the live observers and especially in tests: collect_stream sees only in-turn events, RecordingBroadcaster only the sink's; a test wanting the whole wire picture must combine them, and a stream-only test is e2e for the Agent API but not w.r.t. the durable record (defensive.rs already shows the more-e2e style — assert against events.jsonl). Control stays out of the bus. Only events are unified. The loop's drive (call LLM, dispatch tools, decide next turn) remains ordinary sequential code issuing effects; the server's UI-reaction observers (turn-state, roster, queue snapshots) remain subscribers as they already are. Considered and declined: folding the loop's drive into the event stream (a one-channel actor / event-sourced loop). Rejected because it would make the fact/command boundary a maintained typing discipline rather than a structural one (in sequential code an effect is a function call, so it physically cannot land in the log), obscure inherently-sequential turn logic, and reintroduce the ordering/backpressure that the pull loop gives for free. Invariants to preserve: (a) inputs are peers, not projections — the loop folds over events ⊕ the external input queue (user / monitor), which is not derivable from emitted events; (b) commands are not events — an effect (“call the LLM”) must never reach events.jsonl, or replay/resume would re-execute it. Sequencing — tests first, as the enabler: point agent tests at the unified projection (a recorder / events.jsonl) instead of the run-stream; because tests then assert on the projection rather than the emission mechanism, the emission internals can be unified behind them without rewriting the suite. Spike the event/control split (what is fact vs effect on today's run-stream) before committing — same discipline as the seam work.
  2. Per-monitor timeout_ms (bounded wait / runaway guard). Deferred to evidence; the bounded-wait gap is mapped in §2.2. A per-monitor deadline that auto-stops a job/monitor after N ms — the one piece that would give back wait_for_output's timeoutMs safety (“never hang forever”) without a blocking tool, and simultaneously bounds runaway monitors. Today the equivalent is a timeout N … wrapper inside the command. Lowest-risk, highest-leverage of the deferred cluster — add on first evidence of an unbounded wait or a stuck job.
  3. Action-vs-effect completeness (schema-wide policy). The log is inconsistent about recording the action vs the effect. Sharpest case: monitor stdout — queue time (action) is computed as InputQueueItem.enqueued_at for the live queue-viz but discarded at delivery; only MonitorDeliveryEvent.time (effect) is persisted. Inspection step: enumerate every OmegaEvent variant, classify action / effect / both, decide a documented rule. Low cost, high conceptual payoff.
  4. Reconsider auto-stop of chatty monitors. Dropped by explorative minimalism; kept by Claude Code (confirmed: “monitors that produce too many events are automatically stopped”). Re-add on evidence of the agent leaking/flooding, or keep observing. See §2.1 (Claude's auto-stop).
  5. Per-tool toggle for non-UI sessions. A --tool / --no-tool CLI flag (or config) so headless/scripted sessions toggle individual tools without a custom preset; today only coarse --preset exists server-side.
  6. Live queue/badge polish. Sub-seam real-time queue streaming + per-line badge updates. Seam-aligned already suffices — low-value polish.
  7. Monitors controllable inside the Python REPL. Expose the monitor queue as a Python API so REPL code reacts to events in-session. Speculative; the tool-call boundary is the right abstraction for now.
