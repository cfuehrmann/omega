Async Monitors — Invariants, Decisions & Future Work

CORE SHIPPED This doc keeps only what's needed to move forward: architectural invariants (must-holds), locked-in decisions (must-not-revert), the future menu, and a resume map. The history of how each piece was built lives in the code and its tests.

What exists

An agent can monitor(description, command) to run a background shell command whose stdout lines are injected as role:user at the next seam (no preemption), watch/steer it from the Web UI, and stop_monitor(id). Input (human + monitor) flows through one queue; loop controls are Queue / Halt / Abort, and the UI can delete an individual pending queued prompt before it is delivered. A first-class event sink lets out-of-band events (stderr, control actions) reach events.jsonl + UI when they happen.

1. Invariants & locked-in decisions

Seam & loop correctness (forced by the Anthropic Messages API)

  • Two roles only. Anything not generated by the model (tool results, monitor output, human input) enters as role:user. The synthetic flag is a harness/UI marker only.
  • tool_use → tool_result is rigid — the result is the very next message; nothing inserts between them.
  • Two legal injection seams. Seam A: after end_turn (idle). Seam B: after the tool_result blocks answering a tool_use. The loop drains the input queue only at these two points — so “never inject mid-pair” is structural, not a decision that can be gotten wrong.
  • No context-level preemption. Monitors never interrupt an in-flight message. The only pre-boundary action is Abort (transport-level), kept as a separate explicit interrupt.
  • ⛔ Monitors are out-of-band, never a blocking tool. A long/blocking tool holds Seam B shut → starvation (the wait_for_output problem this feature exists to fix).
  • Single writer for context-bound events — the loop appends; monitors enqueue. (Generalised by the event sink for non-context events — see below.)
  • Park/terminate is defined. Park iff a live monitor or queued item exists, else terminate; never hang when nothing can fire. Parked, the loop selects over {queue item, roster-changed}; roster-changed fires when the live set shrinks without a drainable item (e.g. the last live monitor going away without enqueuing a drainable item while parked).
  • Process-tree reaping on stop() and session end (process-group kill); no orphans.

Contract Authority & schema

  • The Rust OmegaEvent is the canonical schema (crates/omega-types/src/events.rs). Persistence, WS, and UI are derived projections. A semantic change requires a syntactic one (new variant), never a silent alias; update the UI to the types, never the reverse. Old logs failing to deserialize a renamed variant is intended signal, not a bug to paper over.
  • ⛔ Derived projections must be derived, not hand-mirrored. Frontend event frames deserialize straight into OmegaEvent; a drift-guard test round-trips every variant; an unparseable frame surfaces visibly. (Re-introducing a parallel hand-kept WsMessage enum is exactly the drift that made monitor deliveries silently invisible.) Genuinely transport-only envelope frames are the only hand-written part; a new one must not collide tags with an event.
  • Persistence shape. events.jsonl = all events; context.jsonl = derived per-record projection (keyed by ContextHash) that excludes MonitorStderr. Merging consecutive user-role records into one API message is request-assembly (project_messages()), leaving the per-record log un-merged so ContextHash foreign keys stay stable.
  • Projection rules. The fold skips MonitorStderr; MonitorDelivery projects role:user; an unexpected MonitorStopped (StoppedByUser / ProcessExited / ProcessCrashed) projects so the agent learns, while StoppedByAgent and StoppedBySessionEnd do not.
  • Roster is ephemeral — runtime-only, never persisted or reconstructed. WsMessage::MonitorRoster is transport-only (not an OmegaEvent), pushed seam-aligned on connect/reset/resume and after each monitor event.

Unified input model

  • ⛔ One persistent run loop + one InputQueue for human and monitor input, tagged by source. (Do not revert to parking inside send_message: it held the agent lock for the whole turn and deadlocked a fresh UserMessage.)
  • role:user is a projection, not a storage decision. Human messages stay UserMessage, monitor deliveries stay MonitorDelivery; merged late by project_messages(). Human/monitor symmetry falls out for free.
  • Three orthogonal controls: Queue (always enqueue, deliver at next seam), Halt (stop at next seam and wait), Abort (cancel the in-flight block). The retired pause/continue-for-injection machinery is guarded by a source-scan test so it can't grow back.
  • UI kill targets queued prompts only, not live monitors. The UI exposes DeleteQueueItem{enqueued_at} to drop a single pending prompt before it is delivered; there is deliberately no UI kill for a running monitor. Monitors are stopped by the agent (stop_monitor), on natural process exit, or at session end — consistent with the no-auto-stop / visibility-over-control stance. StoppedByUser remains in the schema (and projects when present) but is currently unreachable at runtime; re-add a monitor kill control only on evidence.

Event sink — event-time vs commit-time

  • ⛔ Event-time and commit-time are independent; keep both. Event-time = embedded time / UUIDv7 event_id (when it happened). Commit-time = file/arrival order in events.jsonl (when recorded). Never sort the log by time; the UI shows arrival order with each row's own time. Their divergence is signal (skew/latency/races), not noise.
  • One occurrence = one creation = one time = one event_id, routed to both disk and wire from that single value. Stamp time at the moment of occurrence; append whenever. (Re-deriving a fresh now at broadcast is the double-stamp bug.)
  • Sink contract: emit(event) appends + broadcasts in arrival order, from any caller at any time, with no coordination — EventStore is stateless and its append is O_APPEND/per-line atomic; ws_tx is a multi-producer sender resolved live (replaced on reconnect).
  • User action vs effect. A model/effort change is recorded at action-time (out-of-band, even mid-turn); its effect is turn-aligned — drive_turn snapshots model+effort at entry, so a mid-turn change applies next turn, never to the in-flight one.
  • Phase A (additive sink alongside the loop's path) is shipped; Phase B (sink as the sole emission path) is future work.

Guardrail stance & teaching copy

  • Explorative minimalism. Add only correctness rails; skip the public-serving rails Anthropic adds for a broad audience; iterate by observing the single agent. UI observability is what earns skipping automated kill.
  • Currently dropped (re-add only on evidence): default/max timeout_ms, auto-stop of chatty monitors, line-buffering nagging. Verified prior art (Claude Code) keeps auto-stop + line-buffering — flagged in Future work.
  • No auto-stop — runaway monitors are caught by visibility (logs + UI fired-count), not automation.
  • Teaching copy is load-bearing for usability. Tool descriptions + system-prompt addendum must say: monitor output is not the human; do not fabricate/guess output; after starting, end your turn and wait; stop when no longer needed. The tool result stays neutral bare data (a “stop it when done” sentence tipped Sonnet into killing monitors instantly).
  • Lifecycle decisions. Clean shutdown kills all trees + best-effort MonitorStopped; a hard crash leaves a dangling MonitorStarted (intended forensic signal). Resume forks a new session — no live-monitor inheritance, nothing to reconcile. Headless is benchmark-only, bounded externally + session-end cleanup.

2. Active investigation: blocking wait vs. streaming monitors

Promoted from former future items 3 (“retire/reposition wait_for_output”) and 6 (“one-shot vs streaming split”). They are the same question seen from two ends, so they live together here. Evidence is thin — this section collects findings and frames the decisions; it does not settle them. The premise we already believe: blocking is the smell (wait_for_output stalls the whole agent loop); the open question is what replaces it and whether anything needs adding.

2.1 What Claude Code does (reverse-engineered)

Claude exposes three mechanisms and tells the model to choose by how many notifications it needs — not by “foreground vs background”:

NeedMechanismBehaviour
One — “tell me when the server is ready / the build finishes” Bash with run_in_background:true, command written to exit when the condition is true, e.g. until grep -q "Ready in" dev.log; do sleep 0.5; done Silent while running; one completion notification on exit. Output pulled on demand via BashOutput. Explicit rule: “you'll be notified when it completes — do not poll.”
One per occurrence, indefinitely — “every time an ERROR line appears” Monitor with an unbounded command (tail -f, inotifywait -m, while true) Each stdout line becomes a notification (interrupt). Runs until timeout or TaskStop; persistent:true for session-length watches.
One per occurrence, until a known end — “emit each CI step, stop when the run completes” Monitor with a command that emits lines and then exits Push per line; the watch ends when the command exits.

Supporting cast: BashOutput(bash_id, regex?) = pull output on demand (optional filter); KillShell / TaskStop = kill/cancel; ScheduleWakeup = a fallback heartbeat timer (1200–1800 s) used only as a backstop when a Monitor is the real wake signal. Monitor specifics worth pinning:

  • Timeout is mandatory-ish. “Timeout → killed.” Unbounded commands stay armed until timeout even after the event fired — hence the explicit steer to use run_in_background+until for single notifications, not tail -f | grep -m1.
  • Auto-stop on volume. “Monitors that produce too many events are automatically stopped; restart with a tighter filter.” (Confirms the auto-stop prior art we dropped.)
  • 200 ms batching of stdout lines into one notification; stdout-only triggers (stderr goes to the output file, readable on demand).
  • Heavy script-quality copy: per-line flushing (grep --line-buffered, awk … fflush(), never | head -N), and “silence is not success” — the filter must match every terminal state (crash/hang/OOM), not just the happy path.

The load-bearing finding

Claude has no synchronous blocking wait at all. The “wait for X” use case — the exact thing our wait_for_output exists for — is served by run_in_background + an until loop that exits when the condition is true, yielding one notification. That is a non-blocking wait_for_output: the agent's turn is free to continue or end while the wait happens out-of-band.

Mapping onto Claude's three needs: our monitor covers needs 2 and 3 (streaming, with and without a natural end). Need 1 (one silent notification) has no clean home — see below.

2.3 run_background+monitor vs. Claude's run_in_background

This is the crux of the user's question. The difference is who owns the completion notification:

  • Claude: one tool (Bash+flag) both starts the process and wires its completion notification. The notification fires on the real process's exit; output stays silent and is pulled via BashOutput.
  • Omega: run_background fires nothing on exit. To get a completion signal you must run the work as a monitor (so the monitor process is the job) — but then every stdout line is injected (noisy) unless the command is written to stay silent until done.
  • The equivalent that already works today: monitor("ready", "until grep -q 'Ready' dev.log; do sleep 0.5; done; echo ready"). It stays silent until the condition fires, emits one line, exits → MonitorStopped(ProcessExited) is projected. That is Claude's need-1 pattern, achieved with our existing monitor. So monitor already subsumes wait_for_output's use case — without blocking.

What Omega lacks is Claude's ergonomic need-1: a silent background job that notifies once on completion without the operator hand-writing a silent-until-done loop, and without streaming noise. Open question: is the hand-written loop good enough (explorative minimalism), or is the ergonomic gap worth a dedicated affordance?

2.4 Where wait_for_output's tuned parameters go

The parameters we fine-tuned were tuned for a blocking poll. In a monitor world each becomes a shell idiom inside the command (or a new monitor param):

wait_for_output paramWhy it was tunedMonitor-world equivalent
pattern (JS regex)return as soon as the ready/failure line appearsgrep -qE 'PATTERN' in the loop guard
minBytesreturn once meaningful output exists, no known markerbyte-count check on the log
timeoutMs (required)never hang foreverno monitor equivalent today — needs a timeout N wrapper or a new per-monitor timeout
pid (early-exit)stop waiting the instant the process diesloop must also break on kill -0 $pid || break

The convenience these gave — typed params, no shell-craft, a single clean return object — is the real value of wait_for_output; the blocking is its cost. The decision is whether that convenience is worth keeping a blocking tool, or worth re-expressing as monitor ergonomics.

2.5 Open decisions

  1. Keep, demote, or retire wait_for_output? It is fully subsumed in capability by monitor+silent-loop, but more convenient and harder to misuse for a true one-shot wait. Options: (a) keep + document “prefer monitor for anything you'd resume from”; (b) drop from the default tool selection but leave available; (c) remove. Evidence-driven.
  2. Give monitor a timeout_ms (and maybe persistent)? This is the single missing piece that would let a monitor fully replace wait_for_output (bounded wait) and bound runaway monitors — folding in the old auto-stop concern. Lowest-risk, highest-leverage change in this cluster.
  3. Add a one-shot/silent-completion mode? i.e. close Claude's need-1 ergonomic gap with a flag or a sibling tool, vs. relying on a hand-written silent-until-done command. Decide only after observing whether the agent actually writes those loops correctly.
  4. Auto-stop on volume? Claude does it; we dropped it. Re-add iff we observe flooding.
  5. Pull-on-demand? Claude's BashOutput(bash_id, regex?) has no Omega analogue beyond the agent read_file-ing the logFile — which is arguably already the pull path. Probably no new tool needed.

2.6 Real opportunities to gather data

The blocker is evidence: we need a task the agent wants to wait on and has the opportunity to. Omega's own workflow supplies several — these are where to look first:

  • Mutation testing (cargo mutants) — minutes-to-tens-of-minutes; the agent has a real incentive to react to the first survivor rather than block. The strongest candidate.
  • The gate / full cargo test — slow enough that blocking wastes a turn; a monitor watching for the first failure line is the natural shape.
  • Web-UI dev server (trunk serve / Leptos watch) — a classic “wait for Ready in, then keep tailing for errors” case spanning needs 1 and 2.
  • Long release builds — pure need-1 (“tell me when done”).

Instrumentation question to resolve alongside: what do we record to tell whether the agent chose well (monitor vs. wait_for_output vs. blocking run_command)? The fired-count + commit-time/event-time skew already in the log is a start.

3. Future work (sorted by attractivity)

Ranked by (value × readiness) ÷ (cost × risk). Nothing is scheduled — this is the menu. The wait_for_output/one-shot-vs-streaming pair has been promoted out of this list into §2.

  1. Event sink — Phase B (full unification). Make the sink the sole emission path: the loop emits via sink.emit() too; WS/tests observe the sink, not the run-stream. Cures the “emission coupled to the loop” smell. Main cost = migrating how the test harness observes events (Agent::send_message collects the returned stream). Deliberately gated on whether Phase A earns its keep.
  2. Action-vs-effect completeness (schema-wide policy). The log is inconsistent about recording the action vs the effect. Sharpest case: monitor stdout — queue time (action) is computed as InputQueueItem.enqueued_at for the live queue-viz but discarded at delivery; only MonitorDeliveryEvent.time (effect) is persisted. Inspection step: enumerate every OmegaEvent variant, classify action / effect / both, decide a documented rule. Low cost, high conceptual payoff.
  3. Reconsider auto-stop of chatty monitors. Dropped by explorative minimalism; kept by Claude Code (confirmed: “monitors that produce too many events are automatically stopped”). Re-add on evidence of the agent leaking/flooding, or keep observing. See §2.5.
  4. Per-tool toggle for non-UI sessions. A --tool / --no-tool CLI flag (or config) so headless/scripted sessions toggle individual tools without a custom preset; today only coarse --preset exists server-side.
  5. Live queue/badge polish. Sub-seam real-time queue streaming + per-line badge updates. Seam-aligned already suffices — low-value polish.
  6. Monitors controllable inside the Python REPL. Expose the monitor queue as a Python API so REPL code reacts to events in-session. Speculative; the tool-call boundary is the right abstraction for now.
